# Fidelity notes (honest reading of generated output)

One reader (an AI agent, not a Solana auditor) read the generated handlers of two rewrites against the Solidity, and ran two deliberate mutants through the behaviour check. Generated output: `/tmp/runs/<name>/project` at the time of writing (not committed; re-create with `cmc rewrite --source bench/contracts/<Name>.sol --to solana`).

## LinearVesting (model path, compiled at round 1, 20/20 scenarios)

- Account model: accounts struct, vault and PDA seeds come from code, not from the model. The vault is the associated token account of the config PDA, created in `initialize` and validated as the same ATA everywhere. The vesting program supports one schedule per deployment (config PDA `[b"config"]`), as the Solidity contract is one schedule per contract instance.
- Logic: `fund` keeps the funder and not-revoked checks in order, then the transfer, then `total_allocation += amount`, event. `release` recomputes `vested()` inline with checked u128 arithmetic, requires `amount > 0`, updates `released` before the vault transfer, anyone can call it (the Solidity allows that; the earlier benchmark rewrite required the beneficiary to sign). `revoke` matches: funder-only, once, refund = allocation - vested, state before transfer.
- Differences: `cliff = start + cliffSeconds` is checked_add (reverts on overflow; Solidity 0.8 also reverts, with a panic). Amounts are SPL base units at 9 decimals (the original's 18-decimal amounts are divided by 10^9; the scenarios only use multiples of that). `token` is stored as the mint pubkey. `vested`/`releasable` views are separate view instructions whose result is the transaction return data.
- Not covered: events are not compared field by field (names only are known on the original side); behaviour for non-multiples of the unit conversion; reentrancy (none on Solana here).
- Verdict: faithful on all 20 scenarios, including time jumps at 1 s / 400 s / 1500 s / 5000 s after the last call.

## Uniswap-style StakingRewards, address `0xa148...b711` (model path, compiled at round 1, 25/25 scenarios)

- The 21 KB Synthetix flattened source (SafeMath, Pausable, ReentrancyGuard, permit) was rewritten function by function. Accounting (`updateReward` inlined into every handler, `rewardPerToken`, `earned`) follows the Solidity arithmetic order with checked u128 operations; the 1e18 factor is kept.
- `stakeWithPermit` was translated with an EVM signature (`v, r, s`) as instruction arguments; a permit cannot work on Solana. No scenario exercises it (no successful call exists on the original with the generated arguments), so the report marks it UNCHECKED. Do not trust it.
- The reentrancy guard was ported as a counter stored in config. It is harmless but pointless on Solana.
- Verdict: reward accounting matches the original on 25 scenarios, but it is only checked at 9-decimal-rounded amounts, and `stakeWithPermit`, `notifyRewardAmount`-style owner functions not reached by exploration are unchecked.

## Do the behaviour checks catch the two known bug types?

1. Custom ERC-20 with u64 balances at 18 decimals (supply capped near 18 tokens). The template path prevents it: a plain ERC-20 is never written by the model, it becomes an SPL mint. Experiment: `cmc rewrite --source bench/contracts/ERC20Token.sol --to solana --decimals 18` (a 18-decimal u64 SPL mint, the same numeric flaw): 36 of 37 scenarios cannot be expressed because the initial supply and amounts do not fit u64; the run is labelled FAILED-BEHAVIOUR, not PASSED. With the default 9 decimals it passes with documented differences. Caveat: the check detects this class because the adapter refuses lossy or overflowing amount conversions; it would not notice a custom program that silently wrapped or truncated amounts the adapter chose to pass through.
2. Vault created as a seeded PDA but validated as an ATA. Mutant of the passing LinearVesting rewrite: `fund` validates the vault as a seeded PDA token account while `initialize` still creates the ATA (`packages/translate/scripts/mutant.ts`). The mutant compiles (so compiling alone would pass it) and `anchor build` is clean; the behaviour check ran 20 scenarios: 14 failed with `ConstraintSeeds` (every scenario that funds), 6 passed (the ones that never reach `fund`). The same inconsistency cannot arise from the model any more, because the vault constraints are generated by code from one design decision.

## Bugs the checks found in this pipeline itself (fixed)

Payable instructions did not mark the config account writable (MultiSig `deposit` failed on all 15 scenarios); `address _token` constructor parameters cast to `IERC20` were passed an actor instead of a mint (StakingRewards getReward failed with ConstraintAddress); ERC-721 `maxSupply` was scaled like a token amount; conformance check mis-typed `bytes`/`string` IDL types. All were caught by scenarios or conformance output, none by the compiler.

# Fidelity notes: CosmWasm pack (2026-11-23)

One reader (an AI agent, not a CosmWasm auditor) read generated handlers of two rewrites against the Solidity, and ran the "load instead of may_load" mutant through the behaviour check. Generated output: `/tmp/runs/cw/<name>/project` (not committed; re-create with `cmc rewrite --source bench/contracts/<Name>.sol --to cosmwasm`).

## LinearVesting (model path, compiled first try, 20/20 scenarios)
- Scaffolding vs model: storage, messages, errors, events and the entry points are code. The bodies kept every check and their order (`zero beneficiary`, `bad schedule`, funder/revoked checks), update state before returning the cw20 `Transfer` message, and use checked math everywhere. `vested()` is inlined in `release` and `revoke` with the same branch order as the Solidity.
- `cliff = start + cliffSeconds` is a `u64` checked add (the Solidity does it in uint64 too). `uint64` fields are `u64` in code, `Uint64` strings on the wire.
- Differences: the token pull is `TransferFrom` (the funder must `increase_allowance` first); the token transfer happens after the handler, not inline; `address(0)` as beneficiary is rejected by validation before the handler (the `zero beneficiary` check is also kept, so both paths revert).
- Not covered: events are not compared field by field (names only on the original side); `u64::MAX`-sized schedules.

## Address `0xa148...b711` Uniswap StakingRewards (model path, FAILED-BEHAVIOUR, 20/2/0/3)
- The 21 KB flattened Synthetix source was rewritten function by function. `updateReward` is inlined into each handler with checked `Uint256` arithmetic and the 1e18 factor kept (this is why uint256 stays `Uint256`: with 18 decimals the products exceed u128).
- Real fault found by the scenarios: `exit` skips the `withdraw` zero-amount revert (`if !balance.is_zero()`), so `exit()` with no stake succeeds on CosmWasm and reverts on the original. 2 scenarios fail, the report says FAILED.
- `stakeWithPermit` was translated with `v, r, s` as message arguments (a permit signature cannot be verified this way); no scenario reaches it (no successful call on the original), so it is marked UNCHECKED, do not trust it. `notifyRewardAmount` is also UNCHECKED. The reentrancy guard was ported as a counter that does nothing useful on CosmWasm.
- Verdict: reward accounting matches on 20 scenarios; owner-only and permit paths are unchecked; one real divergence.

## Do the behaviour checks catch the two known bug types?
1. `Item/Map::load` on a missing key (first multisig confirmation always NotFound). Mutant of the passing MultiSig2of3 rewrite: compiles, `cosmwasm-check` passes; the behaviour check fails 16 of 16 scenarios. For StakingRewards 25 of 29. Generation never exposes `load`, so the model cannot write it.
2. Silently dropped zero-address checks (ERC-20). The template path never lets the model write a plain ERC-20 (cw20-base validates addresses). On the model path a `require(x != address(0))` is kept by the model when it appears in the prompt's "checks the Solidity performs" list; messages with `address(0)` are rejected by dispatch anyway, so the revert decision is preserved, and the report lists the zero-address scenarios as documented differences where the original accepted the zero address (e.g. `sweep(address(0))`).

## Pipeline bugs the checks found (fixed)
Comparator treated `uint8` JS numbers and strings as different (MultiSig run 1); template adapter did not read constructor-less name/symbol (address ERC-20 run 1). Both were caught by scenarios, not by the compiler.

# Fidelity notes: Aptos pack (2026-11-23)

One reader (an AI agent, not a Move auditor) read generated modules against the Solidity. Generated output was not committed; re-create with `cmc rewrite --source bench/contracts/<Name>.sol --to aptos`.

## StakingRewards (model path, first-try compile, 29/29 scenarios) and address `0xa148...b711` (25/25)

- Structure comes from code: one `State` resource at a resource account, mapping tables behind `get_staked(account)` / `set_staked(account, v)`, the two reward/stake tokens behind `staking_token_pull` / `reward_token_push`. The model's bodies contain no `borrow_global`, no `acquires`, no framework call except `signer::address_of`, `event::emit` and `vector`/`string` in other contracts.
- Logic: the `updateReward` modifier was inlined into `stake`, `withdraw`, `getReward`, `exit` by the model, each time by hand (about 10 lines each). The arithmetic order of `rewardPerToken` / `earned` is kept with u256 and the 1e18 factor; the original's overflow behaviour is the same (Move aborts). I checked `stake`, `withdraw`, `get_reward`, `exit`: check order, event emission and state-before-transfer order match. In `exit` the model keeps the `require(amount > 0)` of the inlined `withdraw`, as the Solidity does (so `exit` with no stake aborts in both).
- Inlining by the model is the weak point of this pack: the same 10 lines exist in five places, so a model slip in one copy would be a real bug; the scenarios (time jumps, several users) are what protects this, not the structure.
- The framework differences are by design and listed in the report: no `approve`/`transferFrom` (the staker's signer pays), amounts at 8 decimals (the scenarios only use multiples of 10^10 of the original's 18-decimal units).
- Not covered: reentrancy (none on Aptos here), `stakeWithPermit` of the real address (the scenario explorer never found a successful call: the report marks it UNCHECKED), behaviour for amounts that are not multiples of 10^10 (the adapter refuses them: not runnable).

## MultiSig2of3 (model path, one repair round, 16/16)

- `initialize` writes `owners[i]` with the generated fixed-array helper (the array is pre-sized to 3) and keeps the `bad owner` check; `submit`/`confirm` inline `_confirm` and `execute`.
- The low-level `t.to.call{value: t.value}(t.data)` became `native_push(to, value)`; the calldata is NOT executed. The report lists "low-level call calldata / non-value calls" under "Not translated" for submit, confirm, execute. A Safe-style transaction to a contract with calldata would silently do less on Aptos than on Ethereum: do not use this module for that.
- `execute` does not auto-skip on `to == @0x0` (the Solidity does not either). The deposit `receive()` became `deposit(caller, value)` (octas pulled from the caller).

## ERC721Mint (model path, 33/33)

- `mint(value)`: the prologue pulls `value` octas, the body checks `value >= mintPrice`, increments and stores, emits `Transfer`, then refunds the difference with `native_push`. The Solidity `require(ok, "refund failed")` is gone (a failed payout aborts the whole transaction, which is also what the revert did) and the model said so in a DEVIATION comment.
- `tokenURI` builds the string with `u256_to_string`; the original's `_toString` is not re-implemented.
- NFT balances were scaled as plain counts, not token amounts (name based heuristic, the same one the Solana pack fixed after its first ERC721 run).
- It is a hand-rolled ERC-721 in tables, not a Digital Asset: explorers will not list it as an NFT. Only plain ERC-721s (none in the benchmark; the classifier needs a non-payable mint) get the Digital Asset recipe, and that recipe is compiled only, never executed.

## ERC-20 template (`ERC20Token.sol`, `0x4d22...4381`)

- A hand-written Fungible Asset module (`token.move`): `initialize` creates a named object + primary-store-enabled asset and mints the initial supply to the publisher; `transfer` keeps the zero-address assert; `mint` (owner only), `burn` (own balance), `transfer_ownership` (zero-owner assert, event). Verified by 24 passing scenarios and 13 documented ones on the benchmark ERC-20 and 8 + 26 on the real token.
- What the template does NOT do: allowance (`approve`/`transferFrom`/`allowance`/`increaseAllowance`/`decreaseAllowance` do not exist). The benchmark's ERC20Token has the classic "an allowance of 2^256-1 is never decreased" rule; there is no allowance to get wrong, but a Solidity ERC-20 that other contracts pull from cannot be used the same way on Aptos. Events: the framework's Deposit/Withdraw events replace `Transfer`/`Approval`. `totalSupply` is read from the asset's supply (u128).
- A capped / pausable / permit ERC-20 is not matched by the (shared, conservative) classifier, so it goes to the model path as an ordinary contract with its own balance tables (not a Fungible Asset); that path was not run on such a contract here.

## Do the behaviour checks catch the known bug types?

- Dropped access-control assert in `revoke`: caught (1 failing scenario). Cliff / limit ignored: caught (6). Dropped access-control assert in `fund`: NOT caught in that earlier run because the generated unprivileged actor was unfunded and the call aborted for another reason (subsequently fixed by funding the unprivileged actor; see `docs/VERIFICATION.md`). So the check detects missing guards only when some scenario gives the unprivileged actor enough resources to get past the rest of the function.
- "Missing allowance treated as unlimited" (the bug of the earlier free-form ERC-20): not expressible here, because the template has no allowance and the model path pulls through `<token>_pull(caller, ...)`, which moves the caller's own funds; the closest equivalent is a dropped limit/guard (above).
- Amount width: framework amounts are u64 inside the generated helpers (`as u64` aborts above 2^64), and the adapter refuses amounts that are not exact multiples of 10^(18-8) or do not fit u64, so a silently wrapping or truncating rewrite of an 18-decimal supply cannot be mistaken for a pass (it is labelled not runnable, and a template run where most scenarios cannot be expressed is FAILED-BEHAVIOUR).

## Pipeline bugs the checks found in this pack (fixed)

Test time was set twice to the same value (all scenarios aborted in `timestamp`); view return scales were taken from the function name (a struct getter's `value` field compared 10^10 off); JS numbers vs strings in tuple expectations; the initialize prompt exposed generated variables (FAILED-COMPILE on ERC721Mint); scalar helpers were grouped by the Move field name while function usage is by Solidity name, so the prompts of the initial LinearVesting run lacked the state helpers (found by a unit test of the prompt restriction).

# Fidelity notes: Tezos pack (2026-11-23)

One reader (an AI agent, not a Tezos auditor) read generated output of two rewrites against the Solidity, and ran deliberate mutants through the behaviour check. Generated output: `/tmp/runs/tz/<name>/project` at the time of writing (not committed; re-create with `cmc rewrite --source bench/contracts/<Name>.sol --to tezos`).

## MultiSig2of3 (model path, compiled first try, 16/16 scenarios)
- Scaffolding vs model: storage, `initialize` prologue (once, deployer only), "initialized" and "non-payable" checks, array/mapping helpers, the `Tx` record type and every view signature are code. The bodies kept `onlyOwner`, the order of `require`s in `_confirm`/`execute`, the 2-confirmation rule, `executed = true` before the transfer and all events.
- The Solidity `receive()` became the entrypoint `deposit` (a plain transfer to a KT1 would be rejected as "no default entrypoint"; the sender must call `deposit`). `submit` and `confirm` inline `_confirm` and `execute` (three copies of the same logic: the model inlines internal functions, it cannot share them).
- Differences, all flagged in the report: `t.to.call{value: t.value}(t.data)` is a queued native transfer, the calldata is dropped (a Tezos contract cannot execute arbitrary data); `require(ok)` has no equivalent because a failing transfer aborts the whole transaction, which has the same effect; the transfer is executed after the entrypoint returns; `address(0)` as owner is rejected by the same check because the burn address stands in for it.
- A real bug found by READING, not by the scenarios: the first version of the scaffolding treated every array as dynamic (a length counter starting at 0), but `address[3] public owners` is fixed-length and the model's `initialize` writes `owners[i] = o` directly, so the generated public getter `owners(i)` would have aborted with INDEX_OUT_OF_BOUNDS for every index. All 16 scenarios still passed, because the scenario generator exercises declared view functions (`txCount`, `getTx`) but not the getters of public state variables. Fixed (fixed arrays have no length counter, bound = declared length, unset elements read as the default; unit test), but it shows the limit of the behaviour check: generated public getters are checked only by the compiler.
- Verdict: faithful on all 16 scenarios; not covered: public state getters, calldata execution, anything behind more than one confirmation round.

## Uniswap/Synthetix StakingRewards, address `0xa148...b711` (model path, compile round 1, 25/25 scenarios)
- The 21 KB flattened Synthetix source was rewritten function by function. `updateReward` is inlined into every entrypoint with the 1e18 factor as a literal nat; all nat subtractions are `sp.as_nat(..)` so an underflow aborts like Solidity 0.8 (some of them were wrapped by the pipeline, see `NORMALISATIONS.md`).
- `stakeWithPermit`: the EIP-2612 permit call on the staking token cannot exist on FA1.2; the model skipped it and said so (`# DEVIATION`), the report marks it `translated-with-differences` and UNCHECKED (no scenario could call it on the original). The caller must approve this contract on the token first.
- `notifyRewardAmount`: Synthetix checks `rewardRate <= rewardsToken.balanceOf(address(this)) / rewardsDuration`. A Tezos entrypoint cannot read another contract's balance inline, so the check is DROPPED (flagged in the report and in a code comment). This is a security-relevant guard (it stops the distributor from promising more rewards than are funded); keep an internal accounting variable before using this contract. UNCHECKED by scenarios as well.
- The reentrancy guard was ported as a counter (`guard_counter`) that does nothing useful on Tezos (operations run after the entrypoint, no mid-call re-entry); harmless but pointless, and the model marked it.
- Verdict: reward accounting matches the original on 25 scenarios at the amounts the generator uses (multiples of 1e18 mostly); the two functions above are unchecked and differ by design.

## Template path: ERC-20 -> FA1.2
- Both plain ERC-20s (the benchmark contract and the real address `0x4d22...4381`) pass all scenarios with no documented differences, no model. The first run on the real address FAILED 2 of 34 scenarios (`approve(address(0), x)` and `increaseAllowance(address(0), x)` must revert like OpenZeppelin's `_approve`; the recipe did not check the spender): a recipe bug found by the behaviour check, fixed (the guard is generated when the original's `approve` has an `address(0)` requirement).
- Semantics kept on purpose: `approve` SETS the allowance (the TZIP-7 reference refuses non-zero to non-zero changes: not used), an allowance of 2^256-1 is never decremented (the benchmark's and OpenZeppelin >= 4 behaviour; also what the mock token used by the fixtures does), `transferFrom` is FA1.2 `transfer(from, to, value)` by the spender, the owner cannot move other people's tokens (the SmartPy reference template lets its administrator do that; it is not used).
- Not covered: FA1.2 has no `permit`, no `transferFrom` return value, no `Transfer`/`Approval` events (the recipe emits none; FA1.2 indexers read operations/big_map updates), and wallets show FA1.2 less well than FA2.

## Do the behaviour checks catch known bug types? (mutants of passing real rewrites)
1. Access control removed (`revoke` of the LinearVesting rewrite, `scripts/tezos-mutant.ts`): the mutant compiles (a compile check alone would pass it); the behaviour check fails `acl-revoke-14` (revoke() by mallory expected revert, got success). 19 of 20 scenarios still pass.
2. A `require(amount > 0)` removed from `stake` (StakingRewards rewrite): compiles, `rev-stake-04` fails (1 of 29).
3. NOT caught, honestly: removing the `msg.sender == funder` check of `fund` (LinearVesting) or the owner check of `startRewards` (StakingRewards). The scenario's unauthorised caller (`mallory`) holds no tokens and has not approved the contract, so the queued token pull fails anyway and the call still reverts, now for the wrong reason. A scenario that funds the unauthorised caller would catch it; the generator does not. This is a real gap of the check (and of the other packs).
4. Bug classes that cannot arise from the model any more because bodies never see the unsafe construct: reading a missing big_map key (`self.data.m[k]` is rewritten to the defaulting helper), `elif`/`**`/`//` syntax, nat/int arithmetic mix-ups in subtractions (wrapped by code), private-helper arity.

## Bugs the checks found in this pipeline itself (fixed)
Views were evaluated at the simulator's last-call clock, not the scenario step's (the LinearVesting `vested()` view was off by 1-2 s, 3 scenarios failed); the FA1.2 recipe lacked the `approve` zero-address guard (2 scenarios of the real-address ERC-20); two modules both named `main` collide in SmartPy (every scenario of the first end-to-end run was "not runnable": fixture step failed); SmartPy private methods cannot call other private methods (same symptom); the fixed-array getter above. All were caught by scenarios or by running the example, none by the compiler alone except the last one, which was caught by reading.
