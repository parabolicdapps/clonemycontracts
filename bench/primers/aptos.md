APTOS MOVE SYNTAX / FRAMEWORK PRIMER (compile errors seen in practice are listed; avoid them):
- Move is NOT Rust. Variables are mutable by default: write `let x = 0;` then `x = x + 1;` (never `let mut`). No `Self`, no `impl`, no traits, no `&&=`, no `+=` on references except `*r = *r + 1` (compound `+=` is fine on plain locals).
- A module cannot have type parameters (`module app::m<T>` is invalid). Generic *functions* and structs are fine.
- Imports use `use aptos_framework::coin::{Self, Coin};` style. Only these exist (do not invent others): std::{signer, error, string, option, vector, bcs}, aptos_std::{table, smart_table, simple_map}, aptos_framework::{coin, aptos_coin, aptos_account, timestamp, event, account, object, fungible_asset, primary_fungible_store}. Do not call framework functions you are not sure exist; prefer `coin` + `aptos_account` (below) for native value transfers and `aptos_std::table` for mappings.
- Resources: `struct R has key { ... }` stored with `move_to(&signer, R{..})`, read with `borrow_global<R>(addr)` / `borrow_global_mut<R>(addr)` / `exists<R>(addr)`. Any function (including `#[view]`) that calls borrow_global/move_from on R lists `acquires R`; a function that does not touch R directly must NOT list it ("unnecessary acquires annotation"). A `Table` field makes the struct non-droppable: struct needs `has key` only (Table has `store`). Types stored in a resource or table need `store`; `Coin<T>` has `store` but no `drop` (you must deposit/merge/destroy_zero it).
- Table: `table::new<K, V>()`, `table::add(&mut t, k, v)` (aborts if present), `table::contains(&t, k)`, `table::borrow(&t, k)`, `table::borrow_mut(&mut t, k)`, `table::remove(&mut t, k)`, `table::upsert(&mut t, k, v)`. Table has no length/iteration: keep counters yourself.
- Borrow rules: do not hold `&mut v.a` while reading `v.b` through the same reference; copy the value into a local first (`let x = v.b;`), or split into separate steps. Copy only types with `copy` (u64, address, bool, vectors of those...).
- Entry functions take `&signer` first and only primitive-like params (u64, u128, u256, bool, address, vector<u8>, String): never `Coin<T>` or structs as entry params. The caller is `signer::address_of(account)`; there is no msg.value: payments are explicit `coin::withdraw<AptosCoin>(account, amount)` and a `Coin<AptosCoin>` held in a resource field.
- Errors: constants `const E_X: u64 = 1;` and `assert!(cond, error::invalid_argument(E_X))` (error::{invalid_argument, permission_denied, invalid_state, not_found, already_exists}).
- Events: `#[event] struct Foo has drop, store { ... }` and `event::emit(Foo { ... })`. Time: `timestamp::now_seconds(): u64`. Native integer types: u8 u16 u32 u64 u128 u256 (no overflow wrap: arithmetic aborts on overflow). Zero address does not exist as a special value; use `@0x0` only as a sentinel.
- Key framework signatures: coin::withdraw<C>(&signer, u64): Coin<C>; coin::deposit<C>(address, Coin<C>) (receiver must have registered the coin; use aptos_account::deposit_coins<C>(address, Coin<C>) to auto-register); coin::merge(&mut Coin<C>, Coin<C>); coin::extract(&mut Coin<C>, u64): Coin<C>; coin::value(&Coin<C>): u64; coin::zero<C>(): Coin<C>; coin::balance<C>(address): u64; aptos_account::transfer(&signer, address, u64) (APT); aptos_account::transfer_coins<C>(&signer, address, u64).
- Single-contract rule: if the Solidity calls an external ERC-20 token, take the token as a generic parameter `<CoinType>` on functions and hold `Coin<CoinType>` in your resource (struct generic over CoinType, e.g. `struct Pool<phantom CoinType> has key {...}`), instead of inventing other modules.
- Fungible-asset APIs (fungible_asset / primary_fungible_store / object) are intricate and a frequent source of errors; use `coin::Coin<T>` for tokens unless the Solidity contract IS the token. If it is a token, implement balances in your own `Table<address, u64/u256>` resource as the existing ERC-20 translation style (acceptable for this benchmark), noting the DEVIATION.
